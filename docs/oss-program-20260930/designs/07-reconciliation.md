# F1 — Trade comparison algebra and custodian observations

## Outcome and baseline
Make transaction differences reproducible and explainable using the same OSS engine locally and in hosted workflows. The pinned baseline has exact position and settled-cash comparisons, lineage-bearing cash reductions and a cash CLI/Python client. It has no generic trade-matching engine. F1-T01 supplies a deliberately narrow exact trade comparison and pure CSV adapter. It does not require a live custodian connection or the platform trade-log product.

## Financial algebra and projection boundary
Authoritative expected trades are projected from lifecycle-resolved economic events with explicit context and caller-supplied external matching identities. Observations remain a distinct type with separate statement provenance. Comparison produces a report projection of matches and breaks; it never changes a ledger to agree with a statement.

Define immutable validated `TradeProjectionRow` and `TradeObservation` types, a shared exact comparison context, typed diagnostic/break records, and `reconcile_trades` in public reconciliation headers. Do not alias observation and authoritative types. Each expected row retains active economic/lifecycle/source identity and its explicit reconciliation key. The initial key is `(account, external_trade_id)`; this ID is supplied through explicit normalized mapping, not guessed from price, date or internal event identity. Require identical economic/knowledge scope where supported and explicit statement coverage; do not manufacture unsupported historical query semantics.

Compare instrument, signed quantity, price, quote currency, trade date and supplied settlement date exactly. Quantity sign encodes buy/sell consistently with current equity conventions. No FX, tolerance, nearest-time matching, legal netting, lot/P&L calculation, fees or inferred settlement calendar. Reject invalid values, duplicate or ambiguous keys on either side before producing output. One row may list multiple differing fields; report missing observation, unexpected observation and field mismatch deterministically sorted by key. Keep projected evidence and observed evidence separate even for exact matches. Stable rejection diagnostics and owned results must survive caller lifetime.

No associative/commutative law is asserted for matching arbitrary statements. Independent key partitions can be compared and combined only when keys do not overlap and policy/context agree. Financial corrections first pass through O2 lifecycle resolution; a repeated or corrected statement is not an instruction to append another financial event.

## CSV adapter
Add a pure, bounded parser taking explicit text plus source identity, source payload digest and observation context. It returns observations or one structured error; it performs no filesystem/network I/O. Use a closed v1 header: `external_trade_id,account,instrument,quantity,price,currency,trade_date,settlement_date`. Specify strict UTF-8, comma separator, double-quoted fields with doubled quotes, LF/CRLF, no embedded record newline, exact supported decimal formats, size/count limits and rejection of extra/missing/duplicate columns. Parsing repeated identical source text/context yields identical identities and provenance. Row identity derives deterministically from supplied source identity and physical row number; preserve payload digest. Parsing alone does not assert authenticity or implement persistence-level deduplication. Raw source remains caller-owned evidence.

## Delivery and boundaries
First increment owns new trade comparison headers, `libs/adapters/include/luca/adapters/trade_csv.hpp`, focused standalone source/fixtures, and lane-specific documentation. It may add its own isolated compile project but cannot edit root CMake, shared umbrella headers, lifecycle APIs or another lane's files. Optional projection-row construction can accept explicit resolved input/mapping without altering core lifecycle resolution. The platform adapter, live imports, statement replacement policy, wider matching and CLI host are follow-up increments after these interfaces are reviewed.

## Acceptance
Hand-calculated synthetic examples cover an exact match, each differing field, missing/unexpected trades, duplicate and ambiguous keys, opposite sides, multiple currencies, malformed CSV and deterministic repeat parsing. Reports preserve separate evidence and never expose partial output on failure. Include an example of a corrected authoritative trade versus the original statement and a corrected statement as independent evidence. Stable output order, cutoff mismatch and lineage completeness are explicit requirements. These are authored checks; automated execution remains paused. Necessary compilation is allowed. Real custodian-to-platform acceptance remains pending actual supported data and trade-log availability.
